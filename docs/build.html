Reproducible tooling / explicit boundaries

Build the current server tooling

This is not a full engine source build. The public BaseRT source builds a Rust launcher/converter. The current HTTP server is Superfluid, which loads proprietary libbaseRT. No engine download, binary replacement, or inference-model download is performed by these scripts.

Pinned, traceable sources

Verified 2026-11-02. BaseRT's current default branch main and latest release v0.4.3 resolve to the same commit, dated 2026-10-29 UTC. Superfluid is pinned to the release identified as tested by that launcher, not independently upgraded to a moving latest release.

The source lock also pins Rust 1.99.0 and macOS deployment target 15.0. Older Rust 1.91/1.93 cannot compile the pinned Superfluid atomic API. The build rejects non-Apple-Silicon hosts. Although upstream also supports a Linux ARM64 CUDA engine, this component does not implement a Linux adapter. Windows and Intel engine support must not be inferred from the Rust CLI's portability.

Build and rebuild

Install Git, Python 3.9+, Xcode Command Line Tools and rustup. From this repository:

rustup toolchain install 1.99.0 --profile minimal
python3 scripts/build-native.py
python3 scripts/build-native.py --force
python3 scripts/build-native.py --offline --jobs 4

The first invocation checks out the exact source revisions and uses cargo build --locked --release. Subsequent invocations reuse build outputs; --force runs Cargo clean first. Offline mode requires both checkouts and all locked dependencies to be cached already. Dirty source checkouts and unexpected repository origins are rejected, rather than silently discarding local changes.

.build/runtime/
  basert
  basert-serve
  superfluid/bin/superfluid
  superfluid/bin/superfluid-workerd
  superfluid/bin/superfluid-noded
  superfluid/libexec/superfluid/superfluid-worker-basert
  licenses/
  build-info.json

build-info.json records source revisions, Cargo lockfile and output SHA-256 hashes, toolchain, SDK/Xcode, host and target metadata. Rebuilding on a different SDK/host is not guaranteed to be bit-identical. Preserve this metadata with a deployment.

Select the source runtime in 4D

Obtain a compatible engine independently and review its license before use. Preserve its complete matching dylib/symlink, Metal library and notice set. Do not flatten the release archive over the source build: that archive also contains a prebuilt basert.

$options:={\
  model: $home.file("your-model.base"); \
  source_runtime: Folder("/absolute/path/to/BaseRT/.build/runtime"); \
  engine_dir: Folder("/absolute/path/to/licensed/engine"); \
  max_context: 8192; max_tokens: 4096}

The adapter validates the selected paths and sets BASERT_LIB. Its compatibility entry point executes basert serve, selects the staged Superfluid and explicit SUPERFLUID_WORKER_BASERT, and disables auto-installation/update checks. The existing packaged basert-serve and companion binaries are untouched. Omitting source_runtime deliberately retains legacy behavior.

The preserved bundled engine was probed with the source-built server and lacks baseRT_load_tokenizer_only. It is not compatible with this source runtime. A compatible licensed engine must be obtained separately; copying the legacy dylib is not an upgrade.

For direct CLI use, select an explicit engine and local model:

export BASERT_LIB=/absolute/path/to/licensed/engine
.build/runtime/basert-serve /absolute/path/to/model.base \
  --host 127.0.0.1 --port 8080 --max-context 4096 --max-tokens 64

Model and server state use upstream user-cache defaults unless overridden with BASERT_MODELS_DIR and BASERT_STATE_DIR. Keep writable state outside a signed/read-only component bundle.

Validation and limits

python3 scripts/smoke-native.py .build/runtime
python3 scripts/check-docs.py

The native smoke check verifies hashes, the no-engine artifact boundary, CLI version/help, the compatibility entry point, exact worker selection and explicit missing-engine diagnostics without an engine or model download. It does not establish engine ABI compatibility, model readiness, inference quality or 4D host compatibility. With a licensed engine installed, inspect .build/runtime/superfluid/bin/superfluid runtimes --json and start the server with a local model. Check /v1/models, then non-streaming and streaming /v1/chat/completions using the returned model ID. Verify ownership of that server/model; a listing can include unloaded models and is not inference proof. Never substitute a free TCP port or onSuccess for a readiness check.

The native workflow builds only open tooling on a hosted ARM64 macOS runner, then uploads an artifact with notices and metadata. No engine is included and no release is published. Updating pins requires rechecking upstream's tested server release, engine ABI, license and CLI flags.

Licensing and publishing

The wrapper and public CLI/server source use Apache-2.0. Preserve upstream LICENSE/NOTICE files; model weights and transitive dependencies have separate terms. Existing bundled binaries retain their proprietary engine license. The current engine archive also restricts redistribution and third-party hosting. An Apache source build does not remove those restrictions.

Automatic binary publishing is blocked. The legacy component release workflow requires manual dispatch with a default-false permission acknowledgment asserting actual permission to redistribute all included proprietary binaries. That acknowledgment is not itself a license grant. Existing component packaging does not automatically adopt this separate source-runtime output.

Custom Pages deployment

This site is static HTML/CSS under docs/, with a separate GitHub README. It adapts the light sidebar/dark code-block presentation of llama.cpp for 4D without a Jekyll theme, Ruby plugins or external font dependencies. Relative asset links support the /BaseRT/ project path.

After merging, select Settings → Pages → Source: GitHub Actions in this repository. The Pages workflow validates links and uploads the site, then deploys only on main. PR runs cannot deploy. Repository settings and live deployment were not changed by the implementation.

python3 -m http.server 8000 --directory docs
